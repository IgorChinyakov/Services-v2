# Вернуться к Directory Service

Заметка на 16 ноября 2026 года. Фронтовые задания завершены, последнее - DS-F-19: массовые действия с подразделениями.

## Быстрый запуск

Нужны Docker с Compose, Node.js >= 20.9 и npm. Для локальной сборки и тестов бэка нужен .NET SDK 9; для запуска готового Docker-сценария он на хосте не обязателен.

Команды ниже выполняются из корня репозитория `Services-v2`, фронт и бэк - в разных терминалах.

**Бэк и инфраструктура:**

```bash
cd Backend/DirectoryService
docker compose up -d --build --wait
docker compose ps
```

При первом запуске создай `.env` на основе `.env.example` и замени шаблонный пароль. Существующий `.env` не перезаписывай. Compose запускает PostgreSQL, Redis, Seq, backend и nginx; миграции применяются при запуске backend. Фронта в Compose сейчас нет.

**Фронт:**

```bash
cd Frontend/directory-service
npm ci
npm run dev
```

В `Frontend/directory-service/.env.local` должна быть настройка:

```dotenv
NEXT_PUBLIC_API_URL=http://localhost/api/
```

Это адрес API для браузера, не адрес Next.js. Если поменяешь его, перезапусти dev-сервер. При другом `NGINX_HTTP_PORT` укажи соответствующий порт и здесь.

- Интерфейс: `http://localhost:3000`.
- Swagger в Development: `http://localhost/swagger`.
- PostgreSQL для pgAdmin с хоста: `127.0.0.1:5438`; база, пользователь и пароль - из backend `.env`.
- Проверка API: `curl -f 'http://localhost/api/departments?page=1&pageSize=1'`.
- Если API недоступен: `docker compose logs --tail=100 backend nginx postgres` из каталога бэка. `/health` через nginx проверяет сам nginx, а не весь путь до БД.
- Для остановки контейнеров: `docker compose stop`. Не используй `down -v`, если хочешь сохранить данные.

## Что реализовано

- `/locations`: список с обычной пагинацией, создание и редактирование с валидацией, архивирование и восстановление; фильтр по нескольким отделам с сохранением в URL и восстановлением выбора после F5.
- `/departments`: поиск с debounce, фильтр по локациям, пагинация, архив и восстановление, переключение активности с optimistic update, выбор карточек и массовые действия.
- `/departments/[id]`: текущий и новый родитель, превью переноса, вариант без родителя, ошибки выбора и сохранения, возврат в исходный раздел.
- `/departments-workspace-page`: рекурсивное дерево с ленивой загрузкой детей, сохранение раскрытия и выбранного отдела в Zustand; справа позиции и локации выбранного отдела.
- `/positions`: список с курсорной пагинацией и автоматической подгрузкой через IntersectionObserver.
- Глобальный поиск по Cmd/Ctrl+K: debounce, группы сущностей, загрузка, ошибки, пустой результат; переход в раздел с отдельной найденной карточкой через `focusId`.
- Массовые действия отделов: выбор всех на текущей странице без найденной карточки, подтверждение, один HTTP-запрос, полный/частичный успех и ошибки по ID, повтор только оставшихся, блокировки на время запроса.

## Решения, которые важно помнить

- Серверные данные и загруженные дети дерева хранятся в TanStack Query. Zustand хранит UI-состояние дерева и выбранные для bulk ID без persist. Отдельного словаря детей в Zustand нет: повторное раскрытие использует кэш Query, но после устаревания может вызвать запрос.
- Query key включает параметры, влияющие на ответ. Глобальный `staleTime` - 5 минут; устаревание не означает немедленный запрос по таймеру. `invalidateQueries` помечает данные устаревшими и обычно обновляет активные запросы.
- Для локаций URL определяет выбранные ID отделов; локальный массив и запросы по ID дают объекты с названиями для селекта. `value` - выбранные отделы, результаты запроса внутри селекта - варианты выбора.
- Архив подразделения определяется `deletedAt`, активность - отдельным `isActive`. Неактивный отдел не обязательно архивный. Доменную проверку переноса и активности всегда выполняет бэк.
- Optimistic update меняет кэш в `onMutate`, сохраняет снимок и при ошибке откатывает только нужный отдел. Общий refetch ждёт последней связанной мутации, чтобы не затереть другие оптимистические изменения.
- Bulk не использует optimistic update: `200` может содержать ошибки отдельных ID в `result.errors`. При частичном успехе сохраняются изменения успешных отделов, выбранными остаются только неудавшиеся. Выбор сбрасывается при смене страницы, архива и фильтров.
- Тост полного bulk-успеха показывается в хуке до ожидания инвалидаций: обновление последней страницы может очистить выбор и размонтировать диалог. Abort после ответа не отменяет уже сохранённые изменения на сервере.
- `useIsMutating` по ключу `["departments", "bulk"]` блокирует панель и чекбоксы без копирования статуса в отдельный state. Для частичного выбора передаётся `indeterminate`; иконка общего shadcn-компонента оставлена без замены на минус.

## Перед собеседованием

Открой конкретный пример и попробуй объяснить без подсказки:

1. Чем отличаются `useState`, `useRef` и Zustand; что вызывает ререндер, что переживает размонтирование и F5?
2. Когда запускаются эффект и cleanup; как зависимости и замыкания влияют на обработчик IntersectionObserver?
3. Чем отличаются деструктуризация, spread, `map`, `flatMap`, `some` и `every`; почему `[].every(predicate)` даёт `true`?
4. Как связаны управляемый `checked`, `onCheckedChange`, изменение кэша и новый рендер?
5. Как проходит запрос: компонент -> query options -> fetch-функция -> Axios -> Envelope; где обрабатываются транспортные и бизнес-ошибки?
6. Чем отличаются обычная и бесконечная пагинация; откуда берутся `pageParam` и следующий курсор?
7. Как проходят submit формы, валидация, мутация и вывод ошибок; чем отличаются `mutate` и `mutateAsync`?
8. Зачем нужны отмена запросов перед optimistic update, снимок, точечный rollback и инвалидация?
9. Как App Router связывает `[id]`, `searchParams`, навигацию и Suspense; почему URL удобен для фильтров, но не для bulk-выбора?
